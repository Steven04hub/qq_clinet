# QQ AI Bot

这是一个 Python 3.12 + asyncio 项目，用于把普通 QQ 小号、NapCat、OneBot 11 和 OpenAI-compatible AI 服务连接起来。NapCat 负责 QQ 登录及消息收发；Python 负责白名单、@识别、命令、限流、去重、群上下文和模型调用。

默认运行模式会在白名单群中响应 `@机器人`：`echo hello` 用于链路诊断，其它问题调用配置的模型；每个群共享最近的上下文。模型配置缺失时可以使用 `listen`、`echo` 或 `send` 做通信测试。

## 前端控制台（推荐）

先启动并登录 NapCat，再在项目文件夹运行：

```bash
uv sync --locked
uv run --locked python -m app.main web
```

打开 [本地控制台](http://127.0.0.1:8765)，即可设置目标群、工作模式、模型、聊天风格和回复频率，或暂停机器人、清空记忆。**同一时间只运行一个机器人进程**；已运行旧的 `run` 命令时，先在对应终端按 `Ctrl+C` 停止它，再启动控制台。关闭网页不会停止服务；在运行控制台的终端按 `Ctrl+C` 才会退出。

| 模式 | 发言方式 |
| --- | --- |
| 群助手 | 目标群内 `@机器人 + 问题` 时回答；支持 `/help`、`/status`、`/clear` 和 `@机器人 echo hello` |
| 聊天 | 读取目标群近期文字对话，自行判断是否插话，无需 @；默认幽默搞怪，参考群友的用词和接梗方式，保持 AI 身份 |

聊天模式收到目标群的第一条消息后等待 **5 秒**；期间有新消息，就从最新消息重新等待 5 秒，但从这一轮第一条消息起最多等待 **30 秒**。达到任一截止时间就把这一批消息交给模型判断是否接话。例如在第 0、4、8 秒收到消息，会在第 13 秒判断；持续每隔不到 5 秒来消息，则最迟在第 30 秒判断。30 秒是启动判断的上限，最终发送还需要模型生成时间。

计时到期只触发判断，不强制发言。模型结合当前话题、对话对象和自己的近期发言，遇到已结束、重复、与自己无关的私人对话时可以静默；有自然接梗点、求助或面向全群的邀请时可以主动参与，不因为已经沉默几轮就补偿发言。决定参与时可发送文字、表情或二者组合，每分钟上限继续执行。

思考期间收到的新消息会进入下一轮，独立计算 5 秒和 30 秒；如果下一轮已到期、上一轮仍没完成，取消过时的判断，处理最新一批，不排队补发旧回复。没有新消息时不调用模型，也不会定时自说自话。模型决策格式异常会单独显示运行提示。图片、表情和语音消息也计入聊天活动，但模型只看到类型占位，不能看懂图片或听懂语音。群助手的 @ 问答和 `/help`、`/status`、`/clear` 控制指令仍按原方式处理。

聊天决策使用模型服务的 JSON 输出模式，历史中的机器人回复也包装为相同的决策格式，避免多轮聊天后模型输出普通文字而被校验器丢弃。DeepSeek 支持该方式；使用其他兼容服务时，所选模型也需支持 `response_format: {"type": "json_object"}`（参见 [DeepSeek JSON 输出说明](https://api-docs.deepseek.com/guides/json_mode/)）。群助手模式仍使用普通文本输出。

默认语气适合朋友搞怪群：接梗、吐槽、自嘲、善意互怼和适量粗口，普通玩笑不额外说教，也不反复自报 AI 身份。群助手和聊天模式共用这部分语气指导；聊天模式可在界面继续调整风格。项目没有额外的敏感词封禁表或内容审核接口；模型供应商自己的响应策略由其服务决定，本项目没有关闭它的开关。身份真实性、群消息不能覆盖程序规则、密钥保护、目标群过滤和限频仍分别执行。

聊天模式通常用 5～30 字、1～2 句接话，单条文字硬上限 120 字。避免无关的内存、CUDA、PyTorch 等机器人自嘲梗，不再习惯性补“下一个问题”“你下一句是不是……”之类的主持式结尾。程序会清理常见套话结尾并拦截近期近似复读；具体语气仍取决于所选模型和聊天上下文。

### 长期记忆、RAG 与表情包

控制台版本使用本机 **SQLite 数据库**，无需另外安装数据库服务。除群友画像、绰号和梗之外，还会按当前话题检索已保存的历史原话，再提供给模型接话。这是中文分词及双字索引配合 FTS5/BM25 的文本 RAG，不需要额外的向量模型或向量数据库；运行环境没有 FTS5 时使用兼容的 BM25 检索。它依靠词语、名字和已确认绰号的匹配，不等同于向量语义检索。

检索始终限制在当前目标群，排除当前短期上下文中的消息及机器人自己说过的话，每次最多提供 6 条历史片段，并保留说话人和时间。群梗也按当前话题相关性筛选，不会仅因为“同一个人说过”就塞入无关旧梗。旧消息只是参考资料，不会当作刚刚发生的新消息或程序指令。控制台“有记忆，也有表情。”区域可以手动搜索记忆。

聊天模式支持在一条消息中组合文字、`@群友` 和表情，也可以只发表情。模型只能选择当前群已知成员及表情库里的素材，不允许 `@全体成员`。默认提供少量 QQ 内置表情；在控制台上传 PNG、JPG、GIF 或 WebP 文件（单个最多 8 MB），填上如“无语”“笑死”“吃瓜”这样的名称和标签后，机器人就能按场景选择。不会自动看懂图片内容，素材标签应描述图片的用途。

### 群友画像、绰号与梗记忆

控制台下方的“认得群友，也接得住梗。”区域可读取**当前目标群**的可用历史并更新画像。每次最多从 NapCat 请求 1000 条，实际范围取决于 QQ/NapCat 能返回的记录，不代表全部历史。导入旧消息只用于整理，不会触发补发回复。

- 记录昵称与群名片的历史、原话口头禅、具体话题、句式、互怼方式、幽默习惯和对方明确表达的聊天界限。表情统计包括 Unicode 表情、QQ 表情编号、图片/表情包次数；没有图片识别能力，不猜图片内容。
- 每项模型观察都关联消息证据。画像描述“经常开荤梗、复读某句话”等群内表现，不把玩笑推断成真实私生活；发言很少的人保留有限线索，不虚构完整性格。
- 已观察到的昵称/群名片与手动纠正的绰号可确认对应人；模型推断的绰号显示为“待核实”或“有歧义”。可在界面手动纠正，同名多人会保留歧义，模型后续更新不会覆盖人工确认。
- 群梗记录原始包袱、参与者与接梗线索。群助手和聊天模式都按当前发言者及话题读取相关画像、绰号和群梗，用来接话、变换比喻和创造短反转，不直接念画像报告。
- 分析前先规则去重，再使用当前接入的 AI 挑选有用的原始消息。重复内容保留代表原话和重复次数；身份说明、称呼关系、@ 和上下文衔接等信息优先保留。AI 只选择消息编号，不改写原话；清洗失败时退回规则结果。清洗不删除数据库原记录，界面会显示清洗前后数量。
- 新目标群消息自动保存。启用机器人、连接 NapCat 且当前群尚无画像时，会自动读取可用历史并整理；在新电脑上也按同样方式工作。可在 `.env` 设置 `PROFILE_AUTO_IMPORT=false` 改为手动首次导入。QQ/NapCat 返回哪些历史取决于该电脑上的可用记录，无法保证获取旧电脑的全部记录。
- 新增 40 条真人消息且距上次分析至少 5 分钟后自动整理，无新消息时不额外分析。手动点击更新可再次读取历史。清洗和画像分析会额外使用当前所选模型，画像单次调用最多 8192 输出 token；首次历史按成员和消息窗口分批整理，后续自动整理关注最近消息。格式异常最多重试一次，单批仍失败时保留已有结果并继续其他批次。

数据保存在 `.state/memory/groups.sqlite3`，按群隔离、权限 `0600`，每群最多保留最近 5000 条原始消息。清空短期对话不会删除画像；切群不会把旧群资料带进新群回复。画像与群梗只是有依据的参考，不能保证每次绰号推断或接梗都正确，可以查看证据并纠正。

- **单一目标群**：其他群和私聊在校验、日志、记忆、模型调用之前直接忽略。切换目标群会清空短期对话及界面动态，已有画像仍按群隔离保存在本机。
- **滚动限频**：默认最近 60 秒最多 10 条，可在界面设置为 1～60。两个模式、命令回复及拆分后的每条消息共用上限；达到上限后跳过本轮回复。发送结果不确定或失败也占用一次额度，避免重试刷屏。暂停、清空记忆、切模式或调整上限均不会清零已用额度；进程重启会重置内存计数。
- **模型选择**：从 `.env` 所配服务读取模型列表，也可手填该服务支持的模型 ID。点击“保存设置”立即使用新模型；这不会切换供应商或 API 密钥。
- **立即应用**：暂停、清空记忆及保存设置会取消尚未完成的生成任务；切换群、模式、模型或风格也会清空对话记忆。已经发给 QQ 的消息无法撤回。
- **本地保存**：界面设置保存至 `.state/control.json`，重启保留；目标群聊天记录和画像保存在 SQLite，重启时从数据库恢复近期对话，等待新消息再继续聊天。运行动态仅在内存中。首次启动从 `.env` 导入唯一的白名单群；配置多个群时先暂停，需在界面选择一个目标群。
- **密钥与访问**：密钥仍只从 `.env` 读取，不发送到浏览器。控制台仅监听 `127.0.0.1`，写入接口校验同源及自定义请求头。修改 `.env` 中的密钥或服务地址后需重启。

页面“模型已配置”表示凭据已填写；实际生成失败会在运行提示中显示原因。启动控制台时不会自动发送测试消息。可用 `--port 8767` 更换界面端口，或 `--state-file 路径` 指定独立配置文件。

### 换电脑与备份

在控制台点击 **导出迁移包**，或在项目目录运行：

```bash
uv run --locked python -m app.main memory-export --output qq-memory.zip
```

迁移包包含控制设置、SQLite 聊天记录和检索索引、画像、人工确认的绰号，以及上传的表情包。数据库通过在线备份生成一致快照，可在机器人运行时导出。已有同名导出文件不会被覆盖，重新备份请换文件名。迁移包不打包 `.env` 密钥文件、日志或 QQ 登录资料。

把项目代码和迁移包复制到新电脑，并安装 uv 与 NapCat。项目的 `.venv` 不用复制，新电脑会重新安装依赖；旧电脑的 `.state` 已在迁移包内，无需另外复制。将迁移包放到项目目录，执行：

```bash
uv sync --locked
uv run --locked python -m app.main memory-import --archive qq-memory.zip --state-dir .state-restored
cp .env.example .env
```

使用编辑器填写新电脑上的 NapCat 连接凭据和模型密钥，再运行：

```bash
uv run --locked python -m app.main web --state-file .state-restored/control.json
```

导入目录必须是尚不存在的新目录，避免覆盖已有记忆。导入会检查文件哈希、格式版本与数据库完整性；导入后的机器人默认暂停，在控制台确认目标群和连接后再启用。已有 `.env` 时直接编辑它，无需再次执行复制命令。未迁移旧记忆时，可直接启动 `web`，从新电脑的可用群历史重新生成画像。

目前建议保留 SQLite：这是适合单个本机机器人的嵌入式数据库，便于备份和移动，参见 [SQLite 文件格式说明](https://www.sqlite.org/onefile.html)。数据库也可以随应用放进 Docker，但数据目录必须挂载持久卷，参见 [Docker volumes](https://docs.docker.com/engine/storage/volumes/)。当前项目只支持连接本机 NapCat、控制台也只监听本机，尚未提供 Docker 部署配置；无需为这一个机器人单独维护数据库容器。

## 架构与文件

```text
QQ群 ↔ 普通 QQ 小号 / NapCat
              ↕ OneBot 11 正向 WebSocket
       Python OneBotClient
              │
              ├── echo 响应 → ActionManager → 等待中的请求
              └── 群消息事件 → EventDispatcher → Router → Session → LLM

手动 send 命令 → send_group_msg → NapCat → QQ群
```

| 文件或目录 | 职责 |
| --- | --- |
| `app/main.py` | 命令行入口、依赖组装、信号处理 |
| `app/config.py` | `.env` 配置读取、校验和密钥类型 |
| `app/web/` | 本机控制 API、设置持久化与前端静态页面 |
| `app/services/control.py` | 控制台机器人运行时、模式切换、取消与单群处理 |
| `app/services/conversation.py` | 聊天模式决策提示词、回复校验与滚动限频 |
| `app/services/profile_store.py`、`memory_search.py` | SQLite 聊天记忆、画像、绰号与中文文本 RAG |
| `app/services/profile_cleaning.py`、`profile_analysis.py` | AI 清洗、分批生成画像与证据校验 |
| `app/services/stickers.py` | QQ 表情及可迁移的本机表情包库 |
| `app/services/portable.py` | 版本化迁移包导出、校验与恢复 |
| `app/onebot/client.py` | WebSocket 连接、唯一接收循环、重连和消息发送 |
| `app/onebot/actions.py` | UUID echo 与 Future 的匹配、请求异常 |
| `app/onebot/events.py` | 校验并记录白名单群消息，忽略机器人自己发出的消息 |
| `app/onebot/models.py` | 群消息、发送者及通用消息段模型 |
| `app/utils/logging.py` | 标准日志和密钥脱敏 |
| `tests/` | 配置、日志、事件和客户端测试 |
| `.env.example` | 无真实凭据的配置模板 |
| `pyproject.toml`、`uv.lock`、`.python-version` | Python 版本、依赖与锁定版本 |
| `SPEC.md` | 完整分阶段规格 |

`app/handlers/`、`app/services/` 和 `app/onebot/messages.py` 负责消息路由、命令、模型调用、限流、去重和群共享内存会话。

## 安装与配置

macOS 已安装 Homebrew 时，可以执行：

```bash
brew install uv
```

其他安装方式见 [uv 官方安装文档](https://docs.astral.sh/uv/getting-started/installation/)。

在项目根目录执行以下命令。`uv sync` 会创建 `.venv` 并安装锁定的运行和开发依赖，后续使用 `uv run` 无需手动激活环境。

```bash
uv python install 3.12
uv sync --locked
cp .env.example .env
```

使用编辑器修改 `.env`：

| 配置项 | 说明 |
| --- | --- |
| `NAPCAT_WS_URL` | 默认 `ws://127.0.0.1:3001`；仅接受 `ws` / `wss` 和 `127.0.0.1`、`localhost`、`::1` |
| `NAPCAT_ACCESS_TOKEN` | 必填；将 `change-me` 替换为自己的强随机 token，必须与 NapCat 一致，不能包含空白 |
| `ALLOWED_GROUP_IDS` | 自己的测试群号；多个群号使用英文逗号分隔，必须为正整数 |
| `ADMIN_QQ_IDS` | 管理员 QQ 号占位；可以留空，第一阶段不使用 |
| `ACTION_TIMEOUT_SECONDS` | 发送请求并等待响应的总超时，默认 10 秒 |
| `CONNECT_TIMEOUT_SECONDS` | 建立连接的超时，默认 10 秒 |
| `LOG_LEVEL` | 默认 `INFO`；可选 `DEBUG`、`WARNING`、`ERROR`、`CRITICAL` |
| `LLM_API_KEY` | 模型服务 API 密钥；只保存在本地 `.env` |
| `LLM_BASE_URL` | DeepSeek 使用 `https://api.deepseek.com` |
| `LLM_MODEL` | DeepSeek 当前聊天模型使用 `deepseek-flash` |
| `LLM_THINKING` | DeepSeek 建议填 `disabled`，降低群聊延迟 |
| `MAX_CONTEXT_MESSAGES` | 每群保留的最近消息数，默认 20 |
| `PROFILE_AUTO_IMPORT` | 控制台模式自动为尚无画像的目标群导入历史，默认 `true` |

空的 `ALLOWED_GROUP_IDS` 表示忽略所有群消息，手动 `send` 命令也会拒绝发送。所有群号和凭据只放在本地配置中，不需要修改源代码。

`LLM_API_KEY`、`LLM_BASE_URL` 和 `LLM_MODEL` 只在默认 `run` 或 `check-model` 时必填；`listen`、`echo`、`send` 不调用模型。

进程环境变量优先于 `.env`。配置在启动时读取，修改后需要重启程序。URL 不允许携带用户名、密码、查询参数或片段；token 使用认证请求头传递。

## NapCat 配置

先按 NapCat 官方说明安装并登录自己的 QQ 小号，确保小号已经加入测试群。NapCat 与 Python 必须在同一台机器上运行。

在 NapCat 网络配置中添加并启用 **WebSocket Server（正向 WebSocket 服务端）**，设置如下：

| 项目 | 值 |
| --- | --- |
| 启用 | `true` |
| `host` | `127.0.0.1` |
| `port` | `3001` |
| `messagePostFormat` | `array` |
| `reportSelfMessage` | `false` |
| `token` | 启用鉴权，填写与 `.env` 相同的强随机 token |

保存配置，按当前 NapCat 版本提示应用或重启。服务端配置字段参见 [NapCat 官方基础配置](https://doc.napneko.icu/config/basic)。本项目明确使用本机地址，不使用文档示例中的公网监听地址。

Python 连接默认根路径 `/`，在同一连接上收事件、调用接口。OneBot 11 的正向 WebSocket 根路径提供这两种能力，请求中的 `echo` 会在响应中原样返回，详见 [OneBot 11 正向 WebSocket 规范](https://github.com/botuniverse/onebot-11/blob/master/communication/ws.md)。

## 启动与发送

启动带控制台、长期记忆、RAG 和主动聊天的机器人，断线后自动重连：

```bash
uv run --locked python -m app.main web
```

仅使用原有的白名单群 `@` 问答模式（不含控制台的画像、RAG、表情包与主动聊天功能）：

```bash
uv run python -m app.main
```

首次运行前可先检查模型凭据（只发一次测试请求，不连接 QQ）：

```bash
uv run python -m app.main check-model
```

只测试不调用模型的 `@机器人 echo hello`：

```bash
uv run python -m app.main echo
```

也可以明确指定监听子命令：

```bash
uv run python -m app.main listen
```

出现 `NapCat connected` 后，在白名单群发送 `@机器人 你好`。默认模式会调用模型并引用原消息回复；`@机器人 echo hello` 会直接回复 `hello`。`INFO` 不记录完整聊天内容；WebSocket 和模型客户端的请求体日志保持关闭。

手动测试发送时，在另一个终端中将 `TEST_GROUP_ID` 设为自己 `.env` 白名单内的一个真实群号：

```bash
TEST_GROUP_ID='替换为自己的白名单测试群号'
uv run python -m app.main send --group-id "$TEST_GROUP_ID" --message 'Phase 1 链路测试'
```

这条命令只发送一次，收到成功响应后输出新消息的 `message_id` 并退出。它会检查目标群白名单；连接失败、请求失败或超时都会报告错误并退出，不会自动重发。超时可能发生在 QQ 已收到消息、但响应未返回时，重试前先检查群内消息，避免重复发送。

若需要引用群内原消息，将监听日志中该消息的 `message_id` 填入变量：

```bash
ORIGINAL_MESSAGE_ID='替换为日志中的原消息ID'
uv run python -m app.main send \
  --group-id "$TEST_GROUP_ID" \
  --message 'Phase 1 链路测试' \
  --reply-to "$ORIGINAL_MESSAGE_ID"
```

`--reply-to` 会生成 `reply` 消息段，后接 `text` 消息段；原消息必须来自当前测试群。这只是链路验证命令，不会启用自动回复。

## 客户端工作原理

每条 WebSocket 连接只有一个接收循环。`call_action()` 先创建 UUID `echo` 和对应 Future，再发送 `action`、`params`、`echo`；随后等待 Future，不会额外调用 `recv()`。

接收循环先寻找匹配中的 `echo`，找到则完成对应 Future；其余带 `post_type` 的数据交给事件处理器。因此，先到达群消息事件、后到达接口响应，或多个接口响应乱序到达，都不会把事件误当成响应。非法 JSON、未知响应和不符合要求的群消息会被忽略。消息模型允许未知扩展字段及消息段类型。

事件处理独立执行，不阻塞接口响应接收；同时处理的事件任务有容量上限，超出时记录告警并丢弃新事件，避免异常流量导致任务无限增长。第一阶段不持久化消息，也不提供离线补收。

请求超时抛出 `OneBotTimeoutError` 并清理待响应项。意外断开时，未完成请求收到 `ConnectionError` 并被清空。监听模式按 `1、2、4、8、15、15……` 秒等待重连；连接成功后重置间隔。已经发送的动作不会随着重连被再次发送。

连接使用 `Authorization: Bearer ...` 请求头、连接超时和心跳检测，并显式设置 `proxy=None`，使本机连接不经过系统代理。这些参数来自当前 [websockets asyncio 客户端接口](https://websockets.readthedocs.io/en/stable/reference/asyncio/client.html)；重连间隔由本项目自己控制。

按 `Ctrl+C` 或发送 `SIGTERM` 时，程序停止重连，关闭 WebSocket，取消并等待接收任务、事件任务及未完成请求。连接建立中或重连等待中也能退出。

## 自动化检查

### Jev 的两个独立用途

Jev 一方面在程序内部判断机器人是否适合接话，另一方面可以作为群友使用的决策工具。两条路径的问题和结果分开处理，**内部接话分数不会发到群里**。在项目文件夹的 `.env` 中配置独立的 `TYPESAFE_API_KEY`、`JEV_MODEL=jev-1.13.0` 和 `JEV_TIMEOUT_SECONDS=3`，修改后重启项目；不是系统全局配置。

内部接话判断仅用于 Web 控制台的聊天模式。`JEV_MODE=off` 为默认，不自动调用；`shadow` 与聊天模型并行记录判断，不影响实际回复；`gate` 允许 Jev 跳过明确无需参与的轮次。未知媒体、上下文截断、模糊或矛盾判断、超时、认证失败和限流均回退聊天模型。5 秒／30 秒窗口、目标群、发送额度及旧任务失效检查继续由程序执行。密钥只保存在项目 `.env`，不会出现在页面、活动记录或迁移包中。

先建议用 `shadow`。初次 18 个中文合成场景中，7 个明确判断符合预设标签、11 个需要回退，不能据此认定真实群聊准确率。详见 [方案](docs/jev-reply-gate.md) 和 [初次测试报告](docs/jev-test-report.md)。

运行 `uv run --locked python -m scripts.evaluate_jev` 可重跑合成场景；会调用真实 TypeSafe API，结果保存到 `.state/evals/jev-latest.json`，不会连接 QQ。添加 `--validate-only` 只检查样本。普通 `pytest` 不会调用真实 Jev 服务。

群助手和聊天模式都支持群友自己的 Jev 决策请求；即使 `JEV_MODE=off`，配置了密钥也可以使用。例如在目标群发送：

- `用 Jev 帮我决策一下，今晚要不要再打一局？`：是非问题，无需 @。
- `让 Jev 选一下：火锅还是烧烤？四个人，预算 200 元。`：在提供的选项中判断，并保留条件。
- `@机器人 让那个决策模型帮我选选，今晚看电影还是打游戏？`：结合上下文理解意图，不要求固定动词。
- `/jev 今晚要不要再打一局？`：也支持明确命令，不需要 @。
- `@机器人 我有一个问题，用 Jev 帮我决策一下`：先追问具体问题；同一个请求者在 3 分钟内补充问题，可沿用调用意图，不必再次写 Jev 或 @。

当前聊天模型负责语义识别和整理问题，不再依赖“测试／判断／决策”等动词白名单。提到 Jev 的消息无需 @ 即可进入意图识别；单纯介绍 Jev、询问原理、引用别人的调用句子、明确否定调用，都不会执行。未提供具体问题的 `/jev` 或“用 Jev 测一下”会被追问，不会自动变成内部接话测试。是非题直接判断；选择题需有 2～8 个明确选项；开放问题缺少选项或判断目标时先澄清。

机器人真实调用 Jev 后，引用请求返回用户的问题、答案倾向、选项分布及耗时；模型返回置信度时也显示。分数是模型判断，不是现实发生概率。Jev 不生成自由文本理由，因此不会补造它的解释。失败时明确说明没有拿到结果。历史版本保存的 `source=jev_test` 消息保留在数据库，但从后续生成上下文中排除，避免重复输出旧的内部接话报告。

公开决策请求不走普通聊天的 5 秒／30 秒判断窗口，并取消这轮尚未发出的普通回复。仍遵守目标群、启用状态、用户冷却和每分钟回复上限；不会切换内部接话判断模式。

## 手工验证完整链路

1. 登录 NapCat，确认服务端已启用，token 与 `.env` 一致，机器人小号在测试群内，并将该群号加入 `ALLOWED_GROUP_IDS`。
2. 运行监听命令，确认出现 `NapCat connected`。
3. 使用另一 QQ 账号在测试群发送 `@机器人 echo hello`，确认收到引用回复 `hello`。
4. 发送 `@机器人 你好`，确认收到模型回答，并再次提问确认同群上下文生效。
5. 发送 `/status` 查看模型和上下文数量；发送 `/clear` 后再提问，确认上下文已清除。
6. 需要单独验证底层链路时，运行 `listen` 和带 `--reply-to` 的 `send` 命令。
7. 在非白名单群发送消息，确认没有对应群事件日志；用该群号运行 `send`，确认被白名单检查拒绝。机器人自己的群消息也应被忽略。
8. 停止 NapCat 的 WebSocket 服务，观察 `NapCat disconnected`、`NapCat reconnecting`；重新启动服务，确认恢复 `NapCat connected`，再收发一次消息。
9. 按 `Ctrl+C`，确认进程退出且不再重连。重新启动后，可在另一终端找到这个 Python 进程的 PID，并使用 `kill -TERM "$BOT_PID"` 验证 `SIGTERM`；`BOT_PID` 应设为该进程的实际 PID。连接正常和 NapCat 不可用时都应能退出，且不出现未清理任务告警。

真实 QQ 收发需要由你在自己的账号和测试群中完成上述步骤。本仓库的本地测试不连接真实 QQ。

## 常见问题

| 现象 | 排查方式 |
| --- | --- |
| 提示配置校验失败 | 在项目根目录运行，检查 `.env`、必填 token、群号是否为逗号分隔的正整数，以及数值配置是否大于零 |
| 连接被拒绝或持续重连 | 确认 NapCat 正向 WebSocket 服务已启用，监听地址为 `127.0.0.1`、端口为 `3001`；检查服务是否已保存配置 |
| 握手失败或认证错误 | 确认两端 token 完全一致、没有空格；Python 使用 WebSocket 服务 token，不使用 NapCat 管理界面的登录 token |
| 已连接但没有群消息日志 | 检查 QQ 登录状态、群白名单和 `messagePostFormat=array`；机器人自己的消息、私聊及其他事件不会输出群消息日志 |
| 群消息提示校验失败 | 使用数组消息格式，检查 NapCat 事件中的必要字段；日志只显示校验错误数量，避免泄露原始聊天内容 |
| `send` 拒绝发送 | 确认 `--group-id` 是正整数，并已加入当前进程读取的 `ALLOWED_GROUP_IDS` |
| 接口失败或响应超时 | 检查机器人是否在群内、是否可以发言，以及 NapCat 状态；先在 QQ 确认是否已经送达，再决定是否手动重试 |
| 在 QQ 中 `@机器人` 没有回答 | 检查是否运行默认命令、群号是否在 `ALLOWED_GROUP_IDS`、模型三项配置是否齐全，并确认 `.env` 修改后已重启程序 |

## 本地使用约定

NapCat 只监听 `127.0.0.1`，Python 配置也只接受本机地址。保持 token 鉴权开启，替换示例密码；`.env` 已加入 `.gitignore`，不要提交 QQ 账号凭据、token、API Key 或真实群配置。机器人无需群管理权限。

日志会对配置中的密钥、认证头以及常见 token 字段脱敏。`INFO` 中仍包含群号和用户 QQ 号；`DEBUG` 还会包含聊天文本，分享日志前应删除这些个人信息，调试后恢复 `INFO`。
